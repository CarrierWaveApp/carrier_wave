# Auto-Sync Feature Plan

## Goal

Add an optional periodic auto-sync that runs `syncAll()` on a configurable interval while the app is in the foreground. Off by default — users opt in via Settings.

**Critical constraint:** Auto-sync must never degrade foreground app performance — no UI hitches, no blocking the main thread, no competing with user interaction.

## Performance Analysis

`SyncService` is `@MainActor`, but `syncAll()` already offloads heavy work:
- **Downloads**: Run in a `TaskGroup` — network I/O doesn't block main thread
- **Processing**: `processDownloadedQSOsAsync` runs on a background `ModelActor`
- **Uploads**: Run in parallel task groups, network-bound

Main-thread touchpoints are lightweight `@Published` state updates (`syncPhase`, `isSyncing`, service states). These are cheap.

**Remaining risks and mitigations:**

| Risk | Mitigation |
|------|------------|
| `modelContext.save()` on main after processing | Already brief for incremental syncs; auto-sync will always be incremental (never first sync) |
| SwiftUI redraws from `@Published` changes | Same as manual sync — no new overhead |
| Confirmation dialogs blocking the loop | Auto-sync skips when confirmations are pending |
| User taps manual sync during auto-sync | `isSyncing` guard prevents overlap; manual sync waits for next opportunity |
| Auto-sync fires during active logging | Use `Task.priority = .utility` for the sync task so it yields to user-facing work |

## Design

### New Service: `AutoSyncService`

Follow the established `SolarPollingService` pattern:
- `@MainActor @Observable final class` with `shared` singleton
- `configure(syncService:)` called once at startup from `CarrierWaveApp`
- Task-based poll loop with configurable interval
- Re-checks UserDefaults each iteration so toggling in Settings takes effect immediately
- Stops when app backgrounds (via `scenePhase`), restarts when foregrounding
- Skips the tick if a manual sync is already in progress (`syncService.isSyncing`)
- Sync task launched at `.utility` priority to avoid competing with UI work

### UserDefaults Keys

| Key | Type | Default |
|-----|------|---------|
| `autoSyncEnabled` | `Bool` | `false` |
| `autoSyncIntervalMinutes` | `Int` | `15` |

### Interval Options

Picker with fixed choices: **5 min, 15 min, 30 min, 60 min**. Default 15 minutes.

### Settings UI

Add a new section in `SyncSourcesSettingsView` (above the service list):

```
Auto-Sync
  [Toggle] Sync automatically
  [Picker] Every: 5 min / 15 min / 30 min / 60 min   (shown only when enabled)
  [Footer] Automatically syncs with all configured services while the app is open.
```

### App Lifecycle Integration

In `CarrierWaveApp`:
1. In the startup `.task`, call `AutoSyncService.shared.configure(syncService:)` after the existing service setup.
2. In the existing `.onChange(of: scenePhase)`:
   - `.active` → `AutoSyncService.shared.resume()`
   - `.background` / `.inactive` → `AutoSyncService.shared.pause()`

### Guard Rails

- **No overlapping syncs**: If `syncService.isSyncing`, skip that tick and wait for the next interval.
- **Minimum cooldown**: Don't sync if `lastSyncDate` is less than 2 minutes ago (prevents rapid re-sync after a manual sync right before a tick).
- **Utility priority**: Sync task runs at `.utility` so the scheduler prioritizes user-interactive work.
- **No background fetch**: This is foreground-only. iOS background refresh is a separate concern.
- **No confirmation dialogs**: If `importConfirmation` or `exportConfirmation` is non-nil (pending user decision), skip that tick entirely rather than blocking.
- **Foreground-only**: Pause on `.inactive`/`.background` so we don't waste resources or trigger iOS background limits.
